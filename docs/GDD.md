## v0.5 개정 요약 — 턴제 폐지

가장 큰 변화는 **AP가 시간에 따라 차오르는 자원이 된 것**이다(클래시 로얄 엘릭서 방식). 이것 하나로 게임의 장르가 바뀐다. 턴을 주고받는 추리 게임에서, **양측이 동시에 움직이는 실시간 전략 게임**이 되었다.

| 항목 | v0.4까지 | **v0.5** |
|---|---|---|
| 진행 | 턴제 (턴당 AP 3) | **실시간.** AP가 2.5초마다 1씩 회복, 최대 10 |
| 행동 제한 | 함선당 턴 1행동 | **함선별 쿨타임** |
| 함대 | 5칸×1, 4칸×2, 3칸×5 | **4칸×3, 3칸×5** (5칸 폐지) |
| 이동 비용 | 1 AP | **3 AP** |
| 단어 길이 | 3~5글자 | **3~4글자** (5글자 폐지) |
| 식별당함 | 회피 기동으로 해제 | **해제 불가. 영구** |
| 제자리 금지 | 직전 함명 재사용 금지 | **같은 칸으로 이동 금지** (함명 중복은 허용) |
| 적 체력 | 항상 표시 | **식별한 함선만 표시** |

§13의 미결정 12건이 전부 결정되었다.

## v0.2 개정 요약 — 근본 구조 수정

v0.1은 **타일마다 숨은 음절이 있다**고 가정했다. 이게 틀렸고, 여기서 모든 모순이 나왔다.

| | v0.1 (폐기) | **v0.2 (확정)** |
|---|---|---|
| 타일이 가진 것 | 초성 + 숨은 음절 | **초성만.** 영구 불변 |
| "글자"의 정체 | 타일의 숨은 음절 | **함선의 이름(함명)** |
| 함명이 정해지는 때 | — | **이동할 때 쓴 단어가 곧 새 함명** |
| 이동 후 글자 지식 | 롤백이 설명 불가 → 원안 수정함 | **함명이 바뀌므로 무효화.** 원안 그대로 성립 |
| 침몰 시 글자 | 원래 있던 걸 공개 | **함명이 타일에 각인되어 지형이 됨** |

이 하나로 초안의 모든 규칙이 모순 없이 맞물린다. 특히 원안의 *"(만약 이동할 경우 다시 초성만 나오는 정보 획득 상태로)"* 는 수정할 필요가 없었다 — **배가 움직이면 이름이 바뀌니 알아낸 글자가 무효가 되는 것**이 정확한 의미였다. v0.1에서 이 문장을 "논리 충돌"로 판단해 고쳤던 것을 철회한다.

## 1. 컨셉

> 안개 속에서 **초성을 읽어 항로를 만드는** 함대전.
> 배는 자기가 지나온 단어를 이름으로 삼고, 침몰하면 그 이름이 바다에 남는다.

일반 배틀십은 "어디를 쏠까"만 묻는다. WordShip은 **이동조차 단어를 성립시켜야 가능**하다. 정보가 없으면 배가 못 움직인다. 그래서 탐지는 정찰이 아니라 **기동력 그 자체**다.

### 핵심 루프

```
탐지 → 초성 확보 → 항로 단어 성립 → 이동(= 함명 교체 + 주변 자동 정찰)
                                        ↓
                                접촉(주황) 발견
                                        ↓
                    식별(함명 추리 → 고정·3배 취약) → 포격 → 침몰
                                                            ↓
                                        함명이 타일에 각인 → 지형이 되어 항로를 바꿈
```

### 이 게임의 세 가지 긴장

1. **움직이려면 알아야 한다** — 정보가 곧 기동력
2. **움직이면 잊힌다** — 이동은 곧 신분 세탁. 적이 알아낸 내 함명이 무효가 된다
3. **쏘면 들킨다** — 포격은 반드시 자기 위치를 하나 노출시킨다

## 2. 보드 & 좌표계

| 항목 | 값 |
|---|---|
| 크기 | 가로 10 × 세로 25 = 250칸 **[원안]** |
| 가로 표기 | `a` ~ `j` **[원안]** |
| 세로 표기 | 각 플레이어 기준 가까운 쪽 `1`, 먼 쪽 `25` **[원안]** |
| 내부 절대 좌표 | `(x: 0~9, y: 0~24)` — 서버는 항상 절대 좌표만 사용 **[보완]** |
| P1 시점 변환 | `row = y + 1` |
| P2 시점 변환 | `row = 25 - y` (렌더링 단계에서만 뒤집음) **[보완]** |
| P1 배치 구역 | 절대 `y 0~9` (P1 기준 1~10행) **[원안]** |
| P2 배치 구역 | 절대 `y 15~24` (P2 기준 1~10행) **[원안]** |
| 중립 해역 | 절대 `y 10~14` (5행). 시작 시 양측 모두 미탐색 **[보완]** |

### 거리 정의 **[보완]**

모든 거리는 **체비쇼프 거리**(8방향 킹 무브)로 통일하고, 함선과의 거리는 **함선이 점유한 타일 중 가장 가까운 타일** 기준으로 잰다.

```
dist(A, B)    = max(|A.x - B.x|, |A.y - B.y|)
dist(ship, T) = min over t in ship.tiles of dist(t, T)
```

초안의 "1칸 이내", "7칸 이내", "n칸 이내"가 모두 이 정의를 따른다.

## 3. 데이터 모델 (핵심)

**글자는 타일이 아니라 함선에 붙어 있다.** 이 한 줄이 전체 설계를 결정한다.

```
타일    초성만 가진다. 생성 시 확정, 끝까지 불변
함선    함명(단어)을 가진다. 이동할 때마다 바뀐다
잔해    침몰한 함선의 함명이 타일에 각인된 것. 영구 고정
```

### 3.1 타일 — L0 진실 레이어 (서버 전용)

```ts
type Tile = {
  onset: string                  // 초성. 예: 'ㅂ'. 생성 시 확정, 영구 불변
  onsetTier: 'MAJOR' | 'MINOR'   // 8:2 비율                        [원안]
  occupantShipId: string | null  // 현재 이 칸을 점유한 함선
}
```

**타일에는 음절이 없다.** 초성이 전부다. 음절은 그 위에 올라온 함선이 가져오거나, 침몰이 각인한다.

### 3.2 타일 — L1 보드 사실 (양측 공개)

```ts
type TileFact = {
  wreck: { syllable: string } | null   // 침몰 각인. 영구        [원안]
}
```

보드 레벨의 공개 사실은 잔해 하나뿐이다. 잔해가 생긴 칸은 그때부터 **음절을 갖는다.**

### 3.3 함선

```ts
type Ship = {
  id: string
  owner: PlayerId
  len: 3 | 4
  hp: number
  tiles: Coord[]        // 점유 타일. 순서 있음 = 함명 읽는 순서
  name: string[]        // 함명의 음절 배열. length === len
                        //   tiles[i]  ↔  name[i]
  cdUntil: number       // 이 시각까지 이 함선은 행동 불가 (쿨타임)  [v0.5]
  identified: boolean   // 식별당함                                [원안]
}
```

**함명(艦名)** — 그 배가 마지막으로 이동할 때 사용한 단어. 배치 시에 최초로 정해지고, 이동할 때마다 교체된다. 길이는 함선 길이와 같다.

### 3.4 타일의 유효 음절

```ts
function effectiveSyllable(t: Coord): string | null {
  if (fact[t].wreck)     return fact[t].wreck.syllable      // 공개·영구·고정
  if (tile[t].occupant)  return ship(t).name[indexIn(ship, t)]  // 비공개·함선과 함께 이동
  return null                                                // 음절 없음. 초성뿐
}
```

세 경우의 성격이 완전히 다르다.

| 출처 | 공개 | 지속 | 단어 판정에 강제되는가 |
|---|---|---|---|
| 잔해 각인 | 양측 공개 | 영구 | **예** — 정확한 음절 일치 강제 |
| 함선 함명 | 비공개 | 그 함선이 이동하면 소멸 | 아니오 — 다른 배는 진입 불가라 무관 |
| 없음 | — | — | 아니오 — 초성만 일치하면 됨 |

### 3.5 지식 레이어 — 3종 분리 (viewer별)

v0.1에서 하나로 뭉쳤던 것을 **성격이 다른 3종으로 분리**한다. 지속성이 다르기 때문이다.

```ts
type Knowledge = {
  // ① 타일 초성 지식 — 영구. 한 번 알면 절대 잊지 않는다
  onsetKnown: Set<Coord>

  // ② 접촉 정보 — 스냅샷. 관측 순간의 사실이며 시간이 지나면 낡는다
  contact: Map<Coord, 'CONTACT' | 'GHOST'>

  // ③ 적 함명 지식 — 휘발성. 그 함선이 이동하면 전부 소멸       [원안]
  shipName: Map<ShipId, (string | null)[]>
}
```

| 지식 | 원안 명칭 | 획득 | 소멸 | 표시 |
|---|---|---|---|---|
| ① 초성 | 정보 획득 | 탐지 / 이동 / 배치 | **없음 (영구)** | `ㅂ` 연한색 |
| ② 접촉 | 주황 하이라이트 | 관측 시 적함 발견 | 재관측 시 비어 있으면 `GHOST` | 주황 / `?` |
| ③ 함명 음절 | 정보 획득+ | 식별 적중 | **대상 함선이 이동하면 전부 소멸** | `별` 진한색 |

> ③이 원안의 *"정보 획득+ (해당 글자를 알아냄(만약 이동할 경우 다시 초성만 나오는 정보 획득 상태로))"* 를 그대로 구현한 것이다. 함선이 이동하면 새 단어를 쓰므로 함명이 통째로 바뀌고, 알아낸 음절은 전부 무효가 되어 화면은 초성 표시로 돌아간다.

### 3.6 접촉 미러링 **[원안]**

> "주황색 하이라이트 된 타일은 상대에게도 표시(탐지 당함 표시)"

`CONTACT`은 **양쪽 뷰에 동시에 기록된다.** 같은 주황색이지만 읽는 의미가 반대다.

| 관찰자 | 의미 | UI 라벨 |
|---|---|---|
| 탐지한 쪽 | "여기 적함이 있다" | 접촉 |
| 탐지당한 쪽 | "내 이 칸이 들켰다" | 피탐 |

이 미러링이 **포격 시 위치 노출**(§9.4)과 맞물려, 피탐 관리가 곧 생존 전략이 된다.

### 3.7 상태 전이표

```
① 초성 지식 (영구, 단조 증가)
   미지 ──탐지 / 이동 인접 / 초기 배치구역──→ 판명   (되돌아가지 않음)

② 접촉 (스냅샷)
   NONE    ──관측: 적함 有──→ CONTACT   (+ 상대 뷰에도 기록)
   CONTACT ──관측: 적함 無──→ GHOST
   GHOST   ──관측: 적함 有──→ CONTACT
   CONTACT ──점유 함선이 이동──→ 표시 유지 (낡은 정보로 남음)
   (any)   ──그 칸이 잔해화──→ NONE      (잔해는 함선으로 판별 안 됨)  [원안]

③ 함명 음절 지식 (휘발성)
   미지 ──식별 적중──→ 판명
   판명 ──대상 함선이 이동──→ 전부 소멸 (함명 교체)                    [원안]
   판명 ──대상 함선이 침몰──→ 잔해 각인으로 승격 (영구·양측 공개)
```

**식별당함과의 연동 [결정 §13-5]** — 식별당한 함선은 **영원히** 이동할 수 없다. 해제 수단이 없다. 즉 **함명이 영구히 얼어붙는다.** 한 번 해독한 음절은 그 배가 침몰할 때까지 유효하고, 포격 정밀 보너스도 계속 살아 있다. 식별은 이 게임에서 가장 무거운 한 방이다.

### 3.8 태그 → 규칙 적용 매트릭스

| 타일 상태 | 이동: 박스 자격 | 이동: 진입 | 식별 대상 | 포격 | 화면 |
|---|---|---|---|---|---|
| 초성 미지 | **불가** — 한 칸이라도 미지면 박스 불성립 **[원안]** | — | 불가 | **가능** (맹목 사격) **[보완]** | 빈 타일 |
| 초성 판명 | 가능 — **초성만** 일치하면 됨 | 가능 | 가능 | 가능 | 초성 1자 |
| 잔해 (`wreck`) | 가능하나 **정확한 음절 일치 강제** **[원안]** | 가능 | 무의미 (함선 아님) | 가능 + **피해 +1** | 음절 + 잔해 프레임 |
| 적함 점유 | 영향 없음 | **진입 실패**(§9.1) | 가능 | 가능 | 주황 (접촉 시) |
| 적함 + 함명 음절 판명 | 영향 없음 | 진입 실패 | 가능 + 해당 음절 자동 확정 | 가능 + **피해 +1** **[보완]** | 음절 진한색 |
| 아군 점유 | 영향 없음 | **불가** (겹침 금지) | — | 오사 불가 → §13 | 함선 스프라이트 |

**핵심 구분 하나**

- **함명 음절 지식은 정보**다 — 알고 있을 뿐, 단어 매칭은 여전히 초성 기준이고 배가 움직이면 사라진다.
- **잔해 각인은 제약**이다 — 양측 공개이며 영구이고, 그 칸을 지나는 모든 단어가 정확한 음절을 써야 한다.

초안의 예시가 정확히 이 구분이다.

> 함명 `별바다` 함선 침몰 → `별`/`바`/`다`가 타일에 각인
> 다른 함선이 `다` 칸을 지나려면 → `다슬기` **가능**, `도시락` **불가** (`ㄷ`만 맞고 `다`가 아님) **[원안]**

### 3.9 렌더링 우선순위 **[보완]**

```
1. 함선 스프라이트 (자함)
2. 상태이상 오버레이 (식별당함 = 적색 십자선)
3. contact 하이라이트 (CONTACT 주황 / GHOST 물음표)
4. 잔해 프레임 (wreck)
5. 글자 레이어 (음절 판명 = 진한색 / 초성만 = 연한색)
6. 기본 타일 배경
```

타일 크기·그리드 스타일은 `DailySudoku` 타일을 계승한다(§12.6).

## 4. 보드 생성

### 4.1 생성하는 것은 초성뿐 **[변경 — v0.1 대비]**

```ts
for each of 250 tiles:
  tier  = rand() < 0.8 ? MAJOR : MINOR          // 8:2               [원안]
  onset = weightedPick(tier === MAJOR ? MAJOR_SET : MINOR_WEIGHTS)
```

v0.1에 있던 "음절 채우기" 단계는 **삭제한다.** 타일은 음절을 갖지 않는다.

| 등급 | 비율 | 초성 |
|---|---|---|
| `MAJOR` | 80% | ㄱ ㄴ ㄷ ㄹ ㅁ ㅂ ㅅ ㅇ ㅈ ㅎ |
| `MINOR` | 20% | ㅊ ㅋ ㅌ ㅍ ㄲ ㅆ ㅉ ㄸ ㅃ |

> **[보완]** `ㄹ`을 MAJOR에 넣었습니다. 어두에서는 두음법칙 탓에 드물지만, 타일 초성은 **단어의 어느 위치에나 쓰이므로** 어두 빈도가 아니라 전체 음절 초성 빈도를 따라야 합니다(`바람`, `사랑`, `다슬기`).

MINOR 내부는 균등 분배하지 않는다. `ㅃ ㄸ ㅉ`는 실사용 음절이 극히 적어 균등 분배 시 데드존이 된다.

```
MINOR 가중치:  ㅊ 0.22  ㅌ 0.18  ㅍ 0.16  ㅋ 0.14  ㄲ 0.12  ㅆ 0.10  ㅉ 0.04  ㄸ 0.03  ㅃ 0.01
```

### 4.2 생성 검증이 v0.1보다 훨씬 중요해졌다 **[보완]**

초성 배치가 **게임의 전부**가 되었다. 잘못 깔린 초성은 곧 움직일 수 없는 배다. 생성 직후 아래를 검사하고, 하나라도 실패하면 시드를 바꿔 재생성한다.

| 검사 | 기준 |
|---|---|
| 항로 밀도 | 전체 직선 박스(길이 3/4/5) 중 성립 단어가 존재하는 비율 ≥ **35%** |
| 길이 5 항로 | 길이 5 박스 중 성립 단어 존재 비율 ≥ **15%** (기함 마비 방지) |
| 데드존 방지 | 같은 행/열에서 MINOR 초성 3연속 금지 |
| 배치 가능성 | 양측 배치 구역 각각에서, 성립 단어가 존재하는 길이 5 박스 ≥ **6개** |
| 초기 기동 보장 | 배치 완료 후, 각 함선이 최소 1개의 합법 이동을 가질 것 (불가 시 재배치 요구) |

### 4.3 결정론적 시드 **[보완]**

`seed → 보드`가 완전히 결정론적이어야 한다. 버그 재현, 리플레이, 같은 판 재대결에 모두 필요하다. `Math.random()` 금지, 자체 PRNG(mulberry32 등) 사용.

## 5. 함선

| 길이 | 수량 | HP | 포격 사거리 | 함명 길이 | 이동 쿨타임 | 성격 |
|---|---|---|---|---|---|---|
| 4 | **3척** | 6 | 5 | **4글자** | 12초 | 주력. 단단하고 멀리 쏘지만 느림 |
| 3 | 5척 | 3 | 3 | **3글자** | 9초 | 정찰·돌파. 빠르고 약함 |

총 8척 / 점유 **27칸** / 총 HP 33.

> **[결정] 5칸 함선 폐지 (§13-2, §13-9)**
> 5글자 단어는 성립 빈도가 너무 낮아 기함이 사실상 마비될 위험이 컸습니다. 실제 측정에서 **스텁 사전으로는 길이 5 함선이 배치조차 실패**했습니다. 5칸을 없애고 4칸을 한 척 더하는 쪽이 이 문제를 규칙 차원에서 제거합니다.
> 부수 효과로 함대가 **단 두 종류**가 되어 역할 구분이 선명해졌습니다 — 4칸은 화력, 3칸은 발.

**함명 길이 = 함선 길이** — 초안의 *"3~5 길이의 단어 박스"* 는 이제 **3~4글자**로 좁혀진다. 4글자가 3글자보다 어렵기 때문에 4칸 함선이 자연히 둔해지고, HP(6 vs 3)와 정확히 반대 방향이라 트레이드오프가 성립한다.

### 5.1 함명 규칙 **[보완]**

| 규칙 | 내용 |
|---|---|
| 최초 부여 | 배치 시 플레이어가 직접 정한다 (= 초안의 "준비된 배") |
| 교체 | 이동할 때 사용한 단어가 **즉시 새 함명이 된다** |
| 제자리 금지 | **같은 칸 집합으로는 이동 불가** (뒤집기 포함). 함명 중복은 허용 **[결정 §13-3]** |
| 유효성 | 항상 §6.2 판정을 통과한 단어. 함명이 곧 현재 위치의 초성과 일치 |
| 중복 | 같은 함명을 두 척이 동시에 가져도 된다 **[결정 §13-4]** |
| 공개 여부 | 비공개. 상대는 식별로만 알아낼 수 있다 |

**함명이 곧 좌표 정보다.** 함명을 완전히 해독하면 그 배가 어느 칸에 어떤 방향으로 있는지가 확정된다(§9.3).

### 5.2 배치 규칙

- 자기 배치 구역 10×10 안에만 놓는다 **[원안]**
- 가로 또는 세로 직선, 대각선 불가
- 함선끼리 겹침 불가. **인접은 허용** (28/100칸 밀도에서 인접 금지는 배치가 거의 불가능)
- 배치 시 각 함선의 **함명을 함께 정한다.** 놓을 자리의 초성과 맞는 단어여야 한다
- 자기 구역 10×10 전체가 초성 판명 상태로 시작 **[원안]**

## 6. 단어 & 사전 시스템

### 6.1 단어 박스 정의 **[보완]**

**단어 박스** = 보드 위 가로 또는 세로로 **연속된 L칸**.

- 이동: `L = 함선 길이`
- 식별: `L = 3~4` (사용 함선 길이와 무관) **[결정 §13-2]**
- 읽는 방향은 **4방향 모두 허용**: 좌→우, 우→좌, 위→아래, 아래→위
  - *사유: 두 플레이어의 세로 좌표가 서로 반대라, 한 방향만 허용하면 같은 박스를 서로 다르게 읽게 되어 혼란이 생깁니다.*
- 대각선 불가. 보드 밖으로 나갈 수 없음

### 6.2 단어 판정 파이프라인

```
입력 "다슬기"
  ↓ ① 정규화       공백·기호 제거, NFC 정규화, 완성형 한글만 허용
  ↓ ② 길이 검사    len(word) == 박스 길이  ?
  ↓ ③ 지식 검사    박스의 모든 칸이 초성 판명 상태  ?                [원안]
  ↓ ④ 칸별 대조    for i:
                      잔해 칸  →  word[i] == wreck.syllable  (정확 일치)  [원안]
                      그 외    →  onset(word[i]) == tile.onset (초성 일치)
  ↓ ⑤ 사전 조회    화이트리스트 등재어인가?
  ↓ ⑥ 정책 필터    고유명사·비속어·제외 범주가 아닌가?               ← §6.4
  ↓ 성립
```

④의 두 분기가 §3.4 "정보 vs 제약" 구분을 그대로 구현한 것이다. **적함이 점유한 칸은 어차피 진입 불가이므로 그 함명은 판정에 관여하지 않는다.**

**경음 대체 불가 [보완]** — 타일 초성이 `ㄲ`이면 단어의 해당 음절 초성도 정확히 `ㄲ`이어야 한다. `ㄱ`으로 대체 불가. MINOR 초성이 어려운 이유다.

### 6.3 사전 인덱스 설계 **[보완]**

잔해 칸이 생기면서 "N번째 음절이 X로 고정된 길이 L 단어"를 빠르게 찾아야 한다.

```ts
byOnsetPattern: Map<"3|ㄷㅅㄱ", WordId[]>     // 길이|초성열
bySyllableAt:   Map<"3|1|슬", WordId[]>       // 길이|위치|음절
words:          WordId -> { text, onsets, pos, tags }
```

박스 후보 = `byOnsetPattern` 조회 후, 잔해 칸마다 `bySyllableAt` 교집합.

**힌트 UI** — 박스를 선택하면 *"성립 가능한 단어 있음 / 없음"* 만 표시하고 **목록은 숨긴다.** 목록을 보여주면 어휘 게임이 아니라 클릭 게임이 된다. (난이도 옵션 `revealCandidates`로 초심자 모드 제공)

**식별용 역방향 인덱스 [보완]** — 식별은 "이 초성열에 맞는 단어 중 상대가 무엇을 골랐을까"를 추리하는 행위다. 후보가 3개뿐인 초성열은 사실상 자동 적중이고, 200개인 초성열은 찍기다. 밸런스 튜닝을 위해 **초성열별 후보 수 분포**를 빌드 시 미리 계산해 둔다.

### 6.4 고유명사 처리

#### 정의

특정 개체 하나를 지시하는 명사. 이 게임에서 **전면 불허**한다.

인명 · 지명 · 국가/행정구역명 · 기관/단체/기업명 · 상표명 · 작품/서비스명 · 종교적 대상 · 역사적 사건/왕조명 · 천체/별자리 고유명

#### 불허 사유

1. **열린 집합이다.** 상표와 작품명은 매일 새로 생긴다. 판정 근거가 존재할 수 없다.
2. **검증이 비대칭이다.** 한쪽만 아는 고유명사는 어휘력이 아니라 지식 편차로 승패를 가른다.
3. **사전 등재 기준이 일정하지 않다.** 표준국어대사전은 일부 지명·인명을 싣지만 수록 기준에 일관성이 없어, 허용하면 "왜 이건 되고 저건 안 되냐"는 분쟁이 무한 발생한다.
4. **판정이 재현 가능해야 한다.** 단어가 곧 항로이자 함명이므로, 양측이 동일 데이터로 동일한 답을 얻어야 한다.

#### 구현: 사전 빌드 파이프라인

```
국립국어원 우리말샘 / 표준국어대사전 덤프
  ↓ ① 품사 필터      품사 = 명사 인 항목만 유지                     ← §6.5
  ↓ ② 고유명사 제외   품사코드 NNP / 범주 '고유명사' 제거
  ↓ ③ 범주 필드 제외  「지명」「인명」「책명」「작품명」「상호」 보유 항목 제거
  ↓ ④ 뜻풀이 휴리스틱 "…의 이름", "…에 있는 시/군/구", "…나라", "…왕조", "…의 호"
                      패턴 매칭 항목을 PROPER_SUSPECT 로 플래그 → 수동 검수 큐
  ↓ ⑤ 외부 교차검증   위키데이터 표제어 대조, P31(instance of)이
                      human / settlement / organization / creative work 인 표기 제외
  ↓ ⑥ 길이 필터      3~4글자만 유지 (함선 길이가 3·4뿐)
  ↓ ⑦ 블록리스트     비속어·혐오 표현 제거
  ↓ 산출물
     dict.words.bin   단어 → 초성열 인덱스
     dict.meta.json   { version, sha256, wordCount, builtAt }
```

**버전 잠금 [보완]** — 멀티플레이 매치 시작 시 양측 `dict.meta.json`의 `sha256`을 대조하고, 불일치하면 매치를 거부한다. 사전이 다르면 게임이 아니다.

## 7. 페이즈 & 진행 (v0.5 실시간)

### 7.1 준비 페이즈 **[원안]**

1. 자기 배치 구역 10×10 전체의 초성이 공개된다
2. 초성을 보고 8척을 배치하면서 **각 함선의 함명을 함께 정한다** (§5.2)
3. 양측 준비 완료 → 전투 시작

시간은 아직 흐르지 않는다.

> **배치는 이미 퍼즐이다.** 8척 전부에 대해 "놓을 자리의 초성과 맞는 단어"를 찾아야 한다.

### 7.2 전투 — 턴이 없다 **[결정 §13-8]**

턴을 없애고 **AP를 시간에 따라 차오르는 자원**으로 바꿨다. 클래시 로얄의 엘릭서와 같다.

| 규칙 | 값 |
|---|---|
| AP 회복 | **2.5초마다 1** |
| AP 상한 | **10** (넘치면 버려진다) |
| 시작 AP | 5 |
| 행동 순서 | 없음. **양측이 언제든 동시에** |

**행동 비용과 쿨타임**

| 행동 | AP | 그 함선의 쿨타임 |
|---|---|---|
| 이동 | **3** | **함선 길이 × 3초** (3칸 9초 / 4칸 12초) |
| 탐지 | 1 | 5초 |
| 식별 | 2 | 8초 |
| 포격 | 1 | 6초 |

쿨타임은 **함선별**이다. 한 함선이 행동하면 그 배만 잠기고 나머지 7척은 자유롭다. 이것이 턴제의 "함선당 1행동" 제한을 대체한다.

### 7.3 이 변경이 만든 것 **[설계 메모]**

**AP가 병목이 된다.** 이동이 3 AP인데 탐지·포격은 1 AP다. 8척이 동시에 손을 벌리면 싼 행동들이 AP를 계속 빨아가고, **이동에 필요한 3을 영영 못 모은다.**

> 프로토타입 봇에서 이게 그대로 재현됐습니다. 탐욕적으로 행동하는 봇은 **15분 동안 한 척도 자기 진영을 벗어나지 못했습니다.** 이동분 3 AP를 먼저 떼어 두도록 고친 뒤에야 전진하기 시작했습니다.

그래서 실시간 전환의 진짜 플레이는 **"지금 쓸 것인가, 이동을 위해 아낄 것인가"** 가 된다. 턴제에서는 매 턴 AP가 초기화되어 안 쓰면 손해였지만, 이제는 **아끼는 것이 전략**이다. 상한 10이 그 위에 천장을 씌운다 — 무한정 모을 수는 없다.

**두 개의 시계** — AP(진영 전체의 공유 자원)와 쿨타임(함선 개별)이 서로 다른 리듬으로 돌아간다. AP가 남아도 쿨타임 때문에 못 움직이고, 쿨타임이 풀려도 AP가 없으면 못 움직인다.

## 8. 상태이상 · 침몰

### 8.1 `식별당함` (IDENTIFIED) — 영구 **[결정 §13-5]**

| 항목 | 내용 |
|---|---|
| 효과 | **이동 불가** + **입는 피해 3배** **[원안]** |
| 부여 | 상대의 식별이 이 함선을 포함하는 박스에 적중 **[원안]** |
| 해제 | **없음.** 침몰할 때까지 지속 **[결정]** |
| 여전히 가능한 것 | 탐지, 포격 |
| 표시 | 양측 모두에게 적색 십자선 |

회피 기동 행동은 삭제됐다.

**무엇을 잃는가** — 식별당한 배는 세 가지를 동시에 잃는다.

1. **기동** — 그 자리에 영원히 고정된다. 상륙 돌파는 그 순간 끝난다
2. **은폐** — 이동으로만 함명을 세탁할 수 있으므로, 상대가 해독한 음절이 영구히 유효해진다
3. **맷집** — 피해 3배. HP 3짜리 정찰함은 정밀 포격 한 방(6)에 죽는다

남는 것은 고정 포대 역할뿐이다.

> **[우려] 이 규칙은 매우 강력합니다.**
> 식별 한 번(2 AP)에 함선 하나가 사실상 전투 불능이 됩니다. 특히 **상륙 돌파와 정면으로 충돌합니다** — 돌파 주자는 적진 깊숙이 들어가야 하는데, 거기서 한 번 식별당하면 영영 멈추고 상대는 천천히 잡으면 됩니다. 방어가 공격보다 훨씬 강해질 수 있습니다.
> 지시대로 구현했고, 밸런스 판단은 미룹니다. 문제가 확인되면 완화 후보는 §13-5의 대안 항목에 남겨 두었습니다.

### 8.2 `침몰` (SUNK) — 함명이 지형이 된다 **[원안]**

HP가 0 이하가 되면 침몰. **그 함선의 함명이 점유 타일에 그대로 각인된다.**

```
for i in 0..len-1:
  t = ship.tiles[i]
  fact[t].wreck = { syllable: ship.name[i] }   // 영구 각인, 양측 공개
  tile[t].occupantShipId = null
  양측 knowledge: contact[t] = NONE            // 함선으로 판별 안 됨   [원안]
  양측 knowledge: 음절 공개 (잔해는 항상 공개)
```

**잔해 칸의 규칙 효과**

| 효과 | 내용 |
|---|---|
| 글자 고정 | 그 칸을 포함하는 모든 단어 박스는 **정확한 음절** 일치 강제 (초성 일치로는 불성립) **[원안]** |
| 진입 | 가능 (함선이 지나갈 수 있음) |
| 점유 판정 | 함선으로 판별되지 않음 → 식별·포격 표적 아님 **[원안]** |
| 포격 피해 | 음절이 공개 상태이므로 그 칸 포격 시 항상 **+1** |

초안 예시 그대로:

> 함명 `별바다` 함선 침몰 → `별`/`바`/`다`가 타일에 각인
> 다른 함선이 `다` 칸을 지나려면 → `다슬기` **가능**, `도시락` **불가**

**후반부 설계 의도** — 침몰마다 3~5개의 확정 글자가 바다에 박힌다. 항로는 점점 좁아지고, 잔해 지대는 음절이 공개되어 있어 포격 보너스 구역이 된다. **침몰지가 위험지대로 변해 전장을 재편한다.** 게임이 진행될수록 보드가 딱딱해지는 것이 이 게임의 종반 리듬이다.

**부수 효과 — 함명 선택이 유언이 된다 [보완]** — 죽을 것 같은 배가 어떤 단어를 걸치고 있느냐가 남을 지형을 결정한다. 흔한 초성의 함명으로 죽으면 적에게 좋은 항로를 남겨주고, 까다로운 음절이면 그 자리가 막힌다. 고급 플레이 요소로 자연스럽게 열린다.

## 9. 행동 상세

모든 행동은 순수 함수로 구현한다: `applyAction(state, action) -> { state, events[] }`

### 9.1 이동 (3 AP · 쿨 길이×3초)

```
전제
  a) 함선이 IDENTIFIED 상태가 아닐 것                          [원안]
  b) 단어 박스 길이 == 함선 길이 (3 또는 4)
  c) 박스가 현재 점유 칸과 완전히 같지 않을 것 (뒤집기 포함)    [결정 13-3]
  d) 박스의 모든 칸이 초성 판명 상태                           [원안]
  e) 박스의 칸 중 최소 1칸이 함선으로부터 체비쇼프 거리 <= 1    [원안]
  f) 입력 단어가 §6.2 판정 파이프라인 전체를 통과
     (함명 중복 제한 없음 — 같은 단어를 다시 써도 되고,
      다른 배와 같은 이름이어도 된다)                          [결정 13-3,13-4]
  g) 박스가 아군 함선과 겹치지 않을 것

실행
  1. 함선을 박스 위치로 옮기고, 입력 단어가 새 함명이 된다      [원안 해석]
  2. 상대가 이 함선에 대해 해독한 음절을 전부 삭제              [결정 13-1]
  3. 함선 타일 + 인접 1칸 전체를 정보 획득
  4. 쿨타임 = 함선 길이 × 3초
  5. 상륙 판정 (§10.1)
```

**적함과 겹치는 박스를 선택한 경우** — 이동 실패. **AP와 쿨타임은 소모된다.** 충돌 칸에 접촉이 생긴다. "들이받아서 찾았다"는 결과다.

**이동의 3중 의미**

| 측면 | 효과 |
|---|---|
| 기동 | 위치 변경 + 상륙 진척 |
| 정찰 | 주변 1칸 자동 판명 (3칸 함선 기준 15칸) |
| **은폐** | 함명 교체 → 상대가 해독한 음절이 통째로 리셋 |

3 AP는 이 세 가지를 한꺼번에 사는 값이다. 그래서 이 게임에서 가장 비싸고, 가장 중요하다.

### 9.2 탐지 (1 AP · 쿨 5초) **[원안]**

```
전제  자기 함선이 점유한 타일 1개 선택
실행  8방향 중 하나 선택 → 그 방향으로 연속 5칸 초성 판명
      (시작 타일 제외, 그 다음 칸부터 5칸)
      적함 점유 칸: contact = CONTACT (상대 뷰 기록)
      보드 밖으로 나가는 칸은 무시 (사거리 손실)
```

가장 싸고 안전한 정보 확보 수단. 다만 **직선 1줄**만 열리므로, 이동(최대 21칸)에 비해 폭이 좁다. 움직일 수 없는 배가 할 수 있는 유일한 일이기도 하다.

### 9.3 식별 (2 AP · 쿨 8초) — 함명 추리 **[원안 + 보완]**

**이 게임에서 가장 언어적인 행동이다.** 상대가 그 자리에서 어떤 단어를 골랐는지를 초성만 보고 맞힌다.

```
전제
  a) 박스의 모든 칸이 자기 함선으로부터 체비쇼프 거리 <= 7      [원안]
  b) 박스 길이 3~4 (사용 함선 길이와 무관)                      [결정 13-2]
  c) 박스의 모든 칸이 초성 판명 상태
  d) 입력 단어가 §6.2 판정 파이프라인을 통과

실행 — 세 효과는 독립적으로 판정
  ① 함선 판정                                                  [원안]
     박스 안에 적함 점유 칸이 있으면
       → 그 함선들에 IDENTIFIED 부여
       → 해당 칸 contact = CONTACT

  ② 음절 판정 — 반드시 칸별 독립 판정                          [보완]
     for i in 0..L-1:
       t = 박스[i]
       if 적함 점유 && word[i] == effectiveSyllable(t):
          knowledge.shipName[shipAt(t)][indexIn(t)] = word[i]

  ③ 접촉 확정 — 박스 전 칸의 함선 유무가 확정된다              [보완]
     적함 있음 → CONTACT,  없음 → GHOST
```

> **[보완] ② 칸별 독립 판정이 필수인 이유**
> 박스 전체가 일치해야 음절을 주면, 정답 단어를 통째로 맞히지 않는 한 아무것도 못 얻습니다. **칸마다 따로 판정**해야 "한 글자씩 좁혀 간다"는 진행도가 생깁니다. `바다새`로 찍었는데 상대 함명이 `바람새`였다면 `바`와 `새` 두 칸을 얻습니다.

> **[보완] ③ 접촉 확정을 넣은 이유**
> 2 AP를 쓰고 적함이 없으면 완전한 손실이 되어 아무도 안 씁니다. "여기엔 없다"는 것도 정보이므로 확정해 줍니다.

**식별의 가치 3층**

| 층 | 내용 |
|---|---|
| 1 | `IDENTIFIED` — 이동 봉쇄 + 3배 피해 + **함명 동결** (주 목적) |
| 2 | 접촉 확정 — 박스 전 칸의 함선 유무 판명 |
| 3 | 함명 해독 — 해당 칸 포격 피해 +1, 누적 시 함선 실루엣 공개 |

**함명 완전 해독 보너스 [보완]**

```
한 함선의 함명을 전 음절 해독하면
  → 그 함선의 점유 칸 전체가 CONTACT으로 공개된다 (길이·방향·위치 확정)
```

함명이 곧 좌표이기 때문에 자연스럽게 따라오는 결과다. 식별을 반복해 한 배를 집중 해독하는 플레이에 명확한 보상을 준다.

**추리 난이도는 사전이 결정한다 [보완]** — 초성열 `ㅂㄷㅅ`에 맞는 3글자 명사가 몇 개인지가 곧 적중률이다. §6.3의 후보 수 분포를 보고, 후보가 너무 많은 구간은 밸런스 조정 대상으로 본다.

### 9.4 포격 (1 AP · 쿨 6초) **[원안 + 보완]**

```
전제  대상 타일이 자기 함선으로부터 체비쇼프 거리 <= n
      n = 함선 길이별 사거리 (3→3, 4→5)
      대상 칸의 정보 상태는 무관 — 미지 칸에도 맹목 사격 가능    [결정 13-6]
      아군 함선은 조준 불가 — 아군은 피격되지 않는다             [결정 13-7]

피해 계산   (기본 + 정밀) × 식별배율
  dmg = 1                                                        [원안]
  if 대상 칸의 음절을 알고 있음:  dmg += 1    (정밀 사격)
  if 피격 함선 IDENTIFIED:        dmg *= 3                       [원안]

결과
  명중  → HP 감소, 대상 칸 접촉 확정
  HP<=0 → 침몰 (§8.2)
  빗나감 → 대상 칸 빈 칸으로 확정

반동 — 포격 시 자기 위치 노출                                     [원안]
  포격한 함선의 타일 중, 상대에게 아직 노출되지 않은 칸 하나를
  랜덤으로 상대에게 공개한다.
```

| 상황 | 피해 |
|---|---|
| 맹목 사격 | 1 |
| 음절 해독된 칸 / 잔해 칸 | 2 |
| 식별당한 함선 | 3 |
| 식별 + 해독 | **6** |

정찰함(HP 3)은 식별당한 상태에서 정밀 포격 한 방(6)에 침몰한다.

#### 피해와 체력은 식별한 함선만 보인다 **[결정 §13-6]**

| 대상 | 사수가 보는 것 |
|---|---|
| 식별하지 않은 적함 | **"명중" 만.** 피해량도 HP도 안 보임 |
| **식별당한** 적함 | 피해량 + **체력 바** |
| 자기 함선 | 항상 전부 |

**왜 중요한가** — 맹목 사격으로 적을 갉아먹는 플레이가 봉쇄된다. 몇 대 때렸는지 모르면 언제 죽일 수 있는지도 모르기 때문에, 포격만으로는 계획을 세울 수 없다. **죽이려면 먼저 식별해야 한다.**

이로써 식별이 두 개의 문을 동시에 연다 — 상대를 **묶고**(이동 불가), 상대가 **보이게** 만든다. 2 AP의 값이 여기서 나온다.

> 맹목 사격 자체는 허용된다. 명중하면 그 칸에 적함이 있다는 것은 알게 되므로 **정찰 수단으로는 여전히 쓸 수 있다.** 다만 반동으로 내 위치가 하나 노출되므로 공짜는 아니다.

## 10. 승리 조건

| 조건 | 내용 |
|---|---|
| **상륙** | 자기 함선이 **자기 기준 25행**에 진입하면 **즉시 승리** **[원안 v0.3 추가]** |
| 전멸 | 상대 함대 8척 전부 침몰 **[보완]** |
| 기권 | 즉시 패배 |
| 접속 종료 | 재접속 유예 120초, 초과 시 몰수패 |

### 10.1 상륙 승리 **[v0.3 추가]**

```
판정 시점  이동 실행 직후
조건       이동한 함선의 타일 중 하나라도 자기 기준 25행에 들어갔을 때
좌표       P1 → 절대 y = 24  |  P2 → 절대 y = 0
결과       즉시 승리. 이후 판정 없음
```

**"자기 기준 25행"이 어디인가** — 상대 배치 구역의 **가장 안쪽 줄**이다. P1의 25행은 P2의 1행이고, 그 반대도 같다. 즉 상대 함대를 뚫고 끝까지 밀고 들어가야 한다.

**이 규칙이 게임을 바꾸는 방식 [설계 메모]**

이전 버전은 순수 소모전이었고, 그래서 25행이라는 깊이가 "교전까지 너무 멀다"는 문제였다. 상륙 승리가 들어오면서 **그 깊이 자체가 목표가 된다.**

| 축 | 내용 |
|---|---|
| 승리 경로가 둘 | 격침(느리고 확실) vs 돌파(빠르고 위험) |
| 전진의 의미 | 전진은 정찰일 뿐 아니라 **승리 조건에 대한 진척** |
| 함선 역할 분화 | 정찰함(3칸, HP 3)이 **돌파 주자**가 된다 — 3글자 단어에 이동 쿨 9초로 가장 빠르다 |
| 방어의 필요 | 무작정 전진만 할 수 없다. 자기 25행 앞을 비워두면 진다 |
| 식별의 새 가치 | 식별당함 = **영구** 이동 불가 = 돌파 즉시 종료. 디버프가 최강의 방어 수단이 된다 (§8.1 우려) |
| 긴장 | 돌파 주자는 HP 3이라 한 번 잡히면 끝. 들키지 않고 가야 한다 |

4칸 함선은 4글자 단어가 필요하고 이동 쿨이 12초라 돌파에 부적합하다. **느리고 단단한 4칸이 화력을 맡고, 빠르고 약한 3칸이 돌파를 노리는** 역할 분담이 규칙에서 자연스럽게 나온다.

**진입 판정 범위 [결정 §13-11]** — **타일 하나라도 닿으면 상륙**이다. 세로로 선 함선은 끝 한 칸만 걸쳐도 승리한다.

**상륙 후 유지 조건 [결정 §13-12]** — 없다. **즉시 승리**다. 턴 개념이 사라졌으므로 "1턴 버티기" 같은 조건을 걸 수 없다.

대신 **속도는 이동 쿨타임이 제한한다.** 3칸 함선의 이동 쿨은 9초이고, 이동 1회에 3 AP(=7.5초치 수입)가 든다. 자기 진영 끝에서 25행까지는 최소 5~6회 이동이 필요하므로, **모든 것이 완벽해도 1분 안쪽으로는 상륙할 수 없다.**

> 프로토타입 측정: 한 척만 집중해서 최단으로 밀어붙였을 때 **15회 이동 / 133초**. 랜덤 봇 대국 평균은 **245초**였습니다. "개빠른 상륙"은 규칙상 불가능합니다.

## 11. 밸런스 수치 — **튜닝은 보류**

> **[v0.3 방침] 밸런스 패치는 뒤로 미룬다.**
> 지금 목표는 "이 게임이 규칙대로 돌아가는가"를 확인하는 것이다. 아래 수치는 **동작 검증용 초기값**일 뿐이고, 좋은 값인지는 따지지 않는다. 기함이 마비되든 식별이 손해든 지금은 상관없다 — **규칙이 의도대로 발동하는지만** 본다.
> 튜닝은 프로토타입이 한 판 끝까지 돌아가는 것을 확인한 뒤에 시작한다.

한 파일에서 튜닝 가능하도록 전부 상수화한다 (`balance.js` → 나중에 `packages/core/balance.ts`).

```js
BALANCE = {
  board:    { w: 10, h: 25, deployRows: 10 },
  onset:    { majorRatio: 0.8 },

  ap:       { max: 10, start: 5, regenMs: 2500 },      // 엘릭서 방식
  cost:     { move: 3, scan: 1, identify: 2, fire: 1 },
  cooldown: { movePerLen: 3000, scan: 5000, identify: 8000, fire: 6000 },

  ships: [
    { len: 4, count: 3, hp: 6, fireRange: 5 },
    { len: 3, count: 5, hp: 3, fireRange: 3 },
  ],
  scan:     { length: 5 },
  identify: { range: 7, minLen: 3, maxLen: 4 },
  damage:   { base: 1, precisionBonus: 1, identifiedMult: 3 },
  reveal:   { enemyHpOnlyWhenIdentified: true },       // §9.4
  move:     { banSameCells: true },                    // §13-3
  win:      { landingRow: 25, landingNeedsFullShip: false },
  gen:      { maxMinorRun: 2 },
}
```

`turnLimit`, `actionsPerShip`, `banPrevName`, `cost.evade` 는 전부 삭제됐다.

**나중에 (지금 아님) 볼 것**

밸런스 튜닝 단계로 넘어갈 때의 체크리스트. 지금 단계에서는 건드리지 않는다.

1. 식별당함이 영구인 것이 과한가 — 방어가 공격을 압도하지 않는지 (§8.1)
2. 식별 적중률 — 초성열당 사전 후보 수 분포가 추리 가능한 범위인가
3. 항로 밀도가 충분한가 — 배가 묶여서 못 움직이는 빈도
4. 이동의 은폐 효과가 너무 강해 식별이 무의미해지지 않는가 (§13-1)
5. 식별(2AP) → 포격 콤보가 너무 결정적이지 않은가
6. **상륙이 유일한 승리 경로가 되지 않는가** — 봇 대국에서 상륙 9 / 전멸 0 이 관측됐다
7. AP 회복 속도와 상한(2.5초/1, 최대 10)이 이동 3 AP와 맞물려 답답하지 않은가

## 12. 구현 로드맵

### 12.1 설계 원칙 — 로컬과 멀티가 같은 코드를 쓴다

```ts
applyAction(state, action) -> { state, events[] }   // 순수 함수, 부수효과 없음
projectState(state, viewerId) -> ViewState          // 지식 레이어 투영
```

- **로컬 모드**: 클라이언트가 엔진을 직접 호출
- **멀티 모드**: 서버가 같은 엔진을 호출하고 이벤트를 브로드캐스트

로컬 단계에서도 반드시 `projectState()`를 거쳐 렌더링해야 한다. 이걸 건너뛰고 상태를 직접 읽으면 멀티 전환 시 **정보 누출 버그가 전부 이때 터진다.** 처음부터 통과시켜야 한다.

### 12.2 치팅 방지 **[보완]**

클라이언트에 **절대 보내지 않는 것**:

```
tile.onset          (아직 판명되지 않은 칸)
tile.occupantShipId (적함)
ship.name           (적함의 함명)  ← 가장 중요
```

적 함명이 유출되면 식별이 무의미해지므로, 이 게임에서 가장 민감한 필드다. 클라이언트는 액션만 전송하고, 서버가 판정 후 결과 이벤트만 내려보낸다.

### 12.3 단계별 구현 — **[v0.3 재정렬]**

| 단계 | 내용 | 산출물 | 상태 |
|---|---|---|---|
| **0. 동작 검증 프로토타입** | 규칙이 의도대로 발동하는지 확인. 밸런스·사전·그래픽 전부 나중 | `prototype/` | **완료 — 자가 검증 48/48** |
| 1. 코어 엔진 정리 | 프로토타입 엔진을 모듈로 분리, 테스트 정비 | `packages/core` | |
| 2. 사전 | 빌드 파이프라인(§6.4), 인덱스, 고유명사 필터 | `packages/dict` | |
| 3. 정식 UI | DailySudoku 타일 스타일 계승 | `apps/web` | |
| 4. 밸런스 튜닝 | §11 체크리스트 | — | |
| 5. 멀티플레이 | WebSocket 서버, 방 매칭, 재접속 | `apps/server` (Render) | |

#### 0단계에서 의도적으로 미루는 것

| 미루는 것 | 프로토타입에서의 대체 |
|---|---|
| **실제 국어사전** | **허용 사전** — 초성만 맞으면 아무 한글 단어나 통과. 사전은 §6과 독립된 부품이라, 없어도 나머지 규칙을 전부 검증할 수 있다 |
| 밸런스 수치 | §11 초기값 그대로 고정 |
| 그래픽·애니메이션 | 최소한의 그리드 |
| 서버·네트워크 | 로컬 단독 |
| 고유명사 필터 | 스텁 단어 목록만 (엄격 모드 테스트용) |

**허용 사전을 기본값으로 둔 이유 — 측정해서 확인함** — 스텁 사전(98단어)으로 자동 배치를 8개 시드에서 시도한 결과 **성공 0 / 실패 8**이었다(길이 5 함선의 초성 조합에 맞는 단어가 없음). 사전이 빈약하면 배가 한 칸도 못 움직이는 정도가 아니라 **게임이 시작조차 안 된다.** 사전은 나중에 끼우면 되는 부품이므로, 0단계에서는 초성 일치만 보고 통과시킨다.

> 이 측정은 §11-1의 "기함 마비" 우려가 실제 위험임을 보여준다. 정식 사전을 붙인 뒤 **길이 5 박스의 성립 단어 비율**을 가장 먼저 재야 한다.

#### 0단계 검증 결과

```
자가 검증      60 / 60 통과        (v0.5 실시간 규칙 포함)
랜덤 봇 10판   상륙 9 / 전멸 0 / 미결착 1 · 평균 245초
최단 상륙      15회 이동 / 133초   (한 척만 집중해 밀었을 때)
```

모든 규칙이 의도대로 발동한다. 다만 **전멸 승리가 0건**인 것은 눈여겨볼 신호다 — 랜덤 봇이 전투를 못한다는 점을 감안하더라도, 승리 경로 하나가 작동하지 않을 가능성이 있다. 밸런스 단계의 1번 관측 대상이다.

### 12.4 로컬 테스트 모드 3종 **[요청 사항]**

혼자 테스트하려면 세 가지가 다 필요하다.

| 모드 | 용도 |
|---|---|
| **샌드박스** | 양측 정보를 전부 보면서 규칙 검증. 시드 고정, 스텝 실행, 상태 덤프. **규칙 디버깅용** |
| **핫싯** | 한 화면에서 번갈아 플레이. 시점 전환 시 마스킹 화면 삽입. **게임 흐름 체감용** |
| **vs 더미 AI** | 랜덤/휴리스틱 봇 상대. **밸런스 측정용** — 자동 대국 1000판 돌려 §11 지표 수집 |

샌드박스에 **시드 고정 + 리플레이**를 반드시 넣는다. §4.3의 결정론적 생성이 여기서 값을 한다.

**봇 설계 메모** — 식별 봇은 "초성열에 맞는 사전 후보 중 빈도 상위 단어를 찍는" 전략으로 시작한다. 이게 사람 플레이어의 기본 전략과 거의 같으므로, 봇 대국의 식별 적중률이 곧 §11-2의 지표가 된다.

### 12.5 디렉터리 구조 제안

```

packages/dict/     사전 빌드 스크립트 + 런타임 조회 + 후보 수 통계
```

### 12.7 Render 배포 유의점

- 무료 플랜은 유휴 시 슬립 → 콜드스타트 지연. 매칭 화면에 웜업 핑 필요
- 인스턴스 재시작 시 메모리 상태 소실 → 진행 중 매치 보존이 필요하면 Redis 또는 경량 영속화
- WebSocket 연결 유지를 위한 하트비트 필수

## 13. 결정된 사항 (v0.5)

12건 전부 확정. 구현·검증 완료.

| # | 항목 | **결정** | 근거 / 비고 |
|---|---|---|---|
| 1 | 이동 시 함명 지식 | **전부 소멸** | 원안 그대로. 이동 = 신분 세탁 |
| 2 | 단어 길이 | **3~4글자** (5글자 폐지) | 5칸 함선 삭제로 해결. 식별 박스도 3~4 |
| 3 | 제자리 금지 | **같은 칸 집합으로 이동 금지** (뒤집기 포함) | 함명 재사용 제한은 폐지 — 같은 이름을 다시 써도 됨 |
| 4 | 동일 함명 2척 | **허용** | 식별 시 혼동이 생기는 것도 게임의 일부 |
| 5 | 식별당함 해제 | **불가. 영구** | 회피 기동 삭제 → §8.1의 우려 참조 |
| 6 | 미지 칸 포격 | **허용.** 단 **피해·체력은 식별한 함선만 표시** | 맹목 사격으로 갉아먹기 봉쇄 |
| 7 | 아군 오사 | **불가** | 아군은 피격되지 않음 |
| 8 | AP | **시간 회복 자원** (2.5초당 1, 최대 10) | 턴제 폐지. 게임 장르가 바뀐 지점 |
| 9 | 기함 마비 우려 | **5칸 함선 삭제로 해소** | |
| 10 | 품사·어휘 정책 | **보류** | 정식 사전 붙일 때 결정 (§6.5는 잠정안) |
| 11 | 상륙 판정 | **타일 하나라도 25행 진입 시 승리** | |
| 12 | 상륙 유지 조건 | **없음. 즉시 승리** | 속도는 이동 쿨타임이 제한 |

### 남은 판단거리

밸런스 단계로 넘어갈 때 먼저 볼 것들. 지금은 건드리지 않는다.

| 항목 | 관측된 신호 | 완화 후보 |
|---|---|---|
| **식별당함 영구 (§8.1)** | 아직 미측정. 방어가 공격보다 과하게 강해질 수 있음 | 이동만 봉쇄하고 배율은 낮추기 / 침몰한 아군 수만큼 해제권 지급 / 시간 경과 해제 |
| **상륙이 지배 전략인가** | 봇 10판 — **상륙 9 / 전멸 0** | 25행 도달에 추가 조건 / 전멸 보상 강화 |
| **AP 상한 10** | 이동 3회분(9)을 겨우 못 모음 | 상한 조정 / 이동 비용 조정 |
| 사전 | 스텁으로는 배치 실패 | §6.4 파이프라인으로 정식 빌드 |
